# 17. 一条样本如何完成闭环

这一章把前面三章串起来，只回答一个问题：

**一条 QA 数据进入 Search-R1 之后，是怎么变成一条 rollout 轨迹，再被打分成 reward 的。**

这条链路如果你能讲清楚，说明你对这个项目的主流程已经基本打通。

---

## 17.1 先给结论：完整闭环长这样

```text
原始 QA 数据
-> 数据处理脚本构造成统一样本格式
-> trainer 读成一个 batch
-> generation manager 驱动模型多轮生成
-> 模型输出 <search> 或 <answer>
-> 如果 search，就调用检索服务
-> 检索结果包装成 <information>
-> 模型继续生成
-> 最终输出 <answer>
-> RewardManager 解码完整序列
-> qa_em.py 提取答案并打分
-> reward 返回给 trainer 做后续 RL 更新
```

这就是 Search-R1 最核心的执行链。

## 17.2 第一步：原始 QA 数据被处理成训练样本

data = {

## 17.4 第三步：trainer 创建 generation manager

当 trainer 需要做 rollout 时，会先构造 `GenerationConfig`：

这说明 rollout 不是直接在 `RayPPOTrainer` 里手写逻辑，而是交给：

- [`search_r1/llm_agent/generation.py`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:25)

## 17.5 第四步：一条 QA 样本开始变成 rollout 轨迹

真正的核心入口在：

- [`generation.py`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:220)

```python
def run_llm_loop(self, gen_batch, initial_input_ids: torch.Tensor) -> Tuple[Dict, Dict]:
```

这个函数控制的是：

```text
一批样本如何一轮轮生成，直到 answer 或达到上限
```

它初始化了几类状态：

```python
original_left_side = {'input_ids': initial_input_ids[:, -self.config.max_start_length:]}
original_right_side = {'responses': initial_input_ids[:, []], 'responses_with_info_mask': initial_input_ids[:, []]}
active_mask = torch.ones(...)
rollings = gen_batch
```

可以这样理解：

- `original_left_side`：原始 prompt
- `original_right_side`：后续所有生成内容
- `active_mask`：哪些样本还没结束
- `rollings`：当前轮实际送进模型的上下文

此时，原始 QA 样本开始进入 rollout 阶段。

---

## 17.6 第五步：模型生成 search/answer 动作

主循环里先调用模型生成：

- [`generation.py`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:243)

```python
rollings_active = DataProto.from_dict({
    k: v[active_mask] for k, v in rollings.batch.items()
})
gen_output = self._generate_with_gpu_padding(rollings_active)
```

生成结果会进入：

- [`_postprocess_responses()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:54)

```python
responses_ids, responses_str = self._postprocess_responses(gen_output.batch['responses'])
```

这里会把生成结果截断到：

- `</search>`
- 或 `</answer>`

也就是说，系统想把“当前轮的动作”单独拎出来。

然后在：

- [`postprocess_predictions()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:407)

用正则解析动作：

```python
pattern = r'<(search|answer)>(.*?)</\1>'
```

所以当前轮模型可能做三种事：

1. 输出 `<search>...</search>`
2. 输出 `<answer>...</answer>`
3. 输出非法格式

到这一步为止，**一条 QA 样本已经不再只是静态数据，而是带动作的 rollout 轨迹了。**

---

## 17.7 第六步：如果模型 search，就调用检索服务

动作执行在：

- [`execute_predictions()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:353)

```python
cur_actions, contents = self.postprocess_predictions(predictions)
search_queries = [content for action, content in zip(cur_actions, contents) if action == 'search']
```

如果动作是 `search`：

```python
search_results = self.batch_search(search_queries)
```

这会调用：

- [`generation.py`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:450)

```python
return requests.post(self.config.search_url, json=payload).json()
```

请求会发到：

- [`search_r1/search/retrieval_server.py`](/Users/icarus/Documents/Search-R1-main/search_r1/search/retrieval_server.py:326)

```python
@app.post("/retrieve")
def retrieve_endpoint(request: QueryRequest):
```

也就是：

```text
模型输出 <search>query</search>
-> generation.py 提取 query
-> HTTP POST 到 /retrieve
-> 检索服务返回文档列表
```

## 17.8 第七步：检索结果变成 observation

检索服务返回 JSON 后，`generation.py` 不会直接把 JSON 喂给模型，而是先格式化。

关键在：

- [`_passages2string()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:460)

```python
content = doc_item['document']['contents']
title = content.split("\n")[0]
text = "\n".join(content.split("\n")[1:])
format_reference += f"Doc {idx+1}(Title: {title}) {text}\n"
```

然后在：

- [`execute_predictions()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:390)

```python
next_obs.append(f'\n\n<information>{search_results.pop(0).strip()}</information>\n\n')
```

所以检索结果最终会变成：

```text
<information>
Doc 1(Title: ...)
Doc 2(Title: ...)
</information>
```

这一步开始，rollout 轨迹里多了：

- 模型动作 `<search>`
- 外部环境返回 `<information>`

这就已经是一个典型的 agent-environment loop 了。

---

## 17.9 第八步：把 observation 拼回上下文，继续下一轮

拿到 `next_obs` 后，系统会更新状态：

- [`generation.py`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:267)

```python
rollings = self._update_rolling_state(
    rollings,
    responses_ids,
    next_obs_ids
)
```

这里的含义是：

```text
旧上下文
+ 当前轮模型输出
+ 当前轮环境返回的 observation
-> 新上下文
```

所以模型下一轮看到的是：

```text
原问题
+ 第 1 轮 <search>...</search>
+ 第 1 轮 <information>...</information>
```

然后它就能继续推理，再决定是继续 search，还是直接 answer。

这就是多轮 rollout 的核心。

---

## 17.10 第九步：当模型 answer，轨迹结束

如果当前轮动作是：

```text
<answer>...</answer>
```

那么在 [`execute_predictions()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:385)：

```python
if action == 'answer':
    next_obs.append('')
    dones.append(1)
```

这说明该样本结束，不再继续下一轮。

在一个 batch 里，不同样本可能在不同轮结束，所以系统用 `active_mask` 跟踪：

- 哪些样本还在继续
- 哪些样本已经完成

---

## 17.11 第十步：rollout 最终被整理成 trainer 可用的输出

循环结束后，调用：

- [`_compose_final_output()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:321)

```python
final_output['prompts'] = left_side['input_ids']
final_output['input_ids'] = torch.cat([
    left_side['input_ids'],
    right_side['responses']
], dim=1)
```

这里会把：

- 原始 prompt
- 所有 response
- attention mask
- position ids
- info mask

整理成一个 `DataProto` 返回给 trainer。

到这一步，原始 QA 样本已经彻底变成了：

```text
一条完整 rollout 轨迹
```

轨迹里面包含：

- prompt
- 模型生成内容
- 搜索动作
- 检索返回信息
- 最终 answer

## 17.12 第十一步：RewardManager 对完整轨迹打分

接下来回到：

- [`verl/trainer/main_ppo.py`](/Users/icarus/Documents/Search-R1-main/verl/trainer/main_ppo.py:41)

```python
def __call__(self, data: DataProto):
```

`RewardManager` 接到的已经不是原始 QA 数据，而是 rollout 完成后的 `DataProto`。

它做的事情是：

1. 取出 prompt 和 response
2. 去掉 padding
3. 拼成完整序列
4. decode 成字符串
5. 找 `ground_truth`
6. 调打分函数

关键代码：

```python
sequences = torch.cat((valid_prompt_ids, valid_response_ids))
sequences_str = self.tokenizer.decode(sequences)
ground_truth = data_item.non_tensor_batch['reward_model']['ground_truth']
data_source = data_item.non_tensor_batch['data_source']
compute_score_fn = _select_rm_score_fn(data_source)
score = compute_score_fn(solution_str=sequences_str, ground_truth=ground_truth, format_score=self.format_score)
```

所以 reward 计算依赖的是：

- rollout 完整文本
- 训练样本里的 `ground_truth`

## 17.13 第十二步：qa_em.py 从完整文本里提取答案并打分

真正的规则打分函数在：

- [`verl/utils/reward_score/qa_em.py`](/Users/icarus/Documents/Search-R1-main/verl/utils/reward_score/qa_em.py:85)

```python
def compute_score_em(solution_str, ground_truth, method='strict', format_score=0., score=1.):
```

它会先调用：

- [`extract_solution()`](/Users/icarus/Documents/Search-R1-main/verl/utils/reward_score/qa_em.py:73)

```python
answer_pattern = r'<answer>(.*?)</answer>'
```

也就是说，它不是随便从模型输出里找答案，而是明确要求答案在：

```text
<answer>...</answer>
```

然后再做 exact match：

```python
if em_check(answer, ground_truth['target']):
    return score
else:
    return format_score
```

所以 reward 打分规则本质是：

- 没有正确提取到 `<answer>` -> 0 分
- 提取到了，但答案不匹配 -> `format_score`，默认通常也是 0
- 提取到了，且和标准答案匹配 -> 1 分

---

## 17.14 第十三步：reward 被写回响应序列末尾

在 [`RewardManager`](/Users/icarus/Documents/Search-R1-main/verl/trainer/main_ppo.py:80)：

```python
reward_tensor[i, valid_response_length - 1] = score
```

这句非常关键。

它说明 reward 不是平均分摊到所有 token，而是：

**把最终 reward 放在 response 的最后一个有效 token 上。**

这是很多 RLHF / sequence-level reward 代码里的常见做法。

---

## 17.15 最终闭环图

把整个流程压缩成一条最核心的调用链：

```text
nq_search.py
-> 构造 QA 样本
-> parquet
-> train_grpo.sh
-> main_ppo.py
-> RayPPOTrainer.fit()
-> GenerationConfig
-> LLMGenerationManager.run_llm_loop()
-> 模型输出 <search> / <answer>
-> retrieval_server.py 返回检索结果
-> generation.py 拼成 <information>
-> rollout 完成
-> RewardManager.__call__()
-> qa_em.compute_score_em()
-> reward_tensor
-> trainer 后续做 RL 更新
```

---

## 17.16 这一章最该记住什么

一句话总结：

**在 Search-R1 里，一条原始 QA 数据先被组织成带 `prompt` 和 `ground_truth` 的训练样本；再通过 `generation.py` 跑成包含 `<search>/<information>/<answer>` 的 rollout 轨迹；最后由 `RewardManager + qa_em.py` 根据最终 `<answer>` 与标准答案的匹配情况计算 reward。**

如果你后面要排查问题，这一章也可以直接给你定位方向：

- 数据格式问题：先看 `nq_search.py`
- 搜索动作问题：先看 `generation.py`
- 检索接口问题：先看 `retrieval_server.py`
- reward 异常问题：先看 `main_ppo.py` 和 `qa_em.py`

# 22. 检索结果如何进入下一轮上下文

这一章只讲一件事：

**模型发起搜索之后，检索结果是怎样一步步变成下一轮 `input_ids` 的。**

这是 Search-R1 里最值得吃透的局部流程之一，因为它直接体现了：

```text
LLM Agent
+ 检索服务
+ 多轮上下文更新
```

这条链如果你讲不清，说明对 `generation.py` 还没有真正吃透。

---

## 22.1 先看整体顺序

代码主线在：

- [`search_r1/llm_agent/generation.py`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:353)

流程可以先压缩成：

```text
模型输出 <search>query</search>
-> execute_predictions() 提取 query
-> batch_search() 调检索服务
-> _passages2string() 把检索结果格式化成纯文本
-> execute_predictions() 包成 <information>...</information>
-> _process_next_obs() 把 observation tokenize
-> _update_rolling_state() 把 response + observation 拼回 input_ids
-> 下一轮模型继续生成
```

下面逐段拆。

---

## 22.2 第一步：当前轮先知道模型想 search

入口在：

- [`execute_predictions()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:353)

```python
cur_actions, contents = self.postprocess_predictions(predictions)
next_obs, dones, valid_action, is_search = [], [], [], []
```

这里的 `predictions` 是模型当前轮生成出来的文本，比如：

```text
<search>Mike Barnett CSKA Moscow general manager</search>
```

`postprocess_predictions()` 会把它拆成：

- `action = "search"`
- `content = "Mike Barnett CSKA Moscow general manager"`

然后在：

```python
search_queries = [content for action, content in zip(cur_actions, contents) if action == 'search']
```

把所有 search query 收集出来。

所以到这里，系统已经从模型输出里拿到了真正的检索词。

---

## 22.3 第二步：batch_search() 调检索服务

看：

- [`batch_search()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:438)

```python
def batch_search(self, queries: List[str] = None) -> str:
    results = self._batch_search(queries)['result']
    return [self._passages2string(result) for result in results]
```

这里分两步：

1. `_batch_search(queries)` 真正发 HTTP 请求
2. `_passages2string(result)` 把返回的文档列表转成字符串

也就是说：

```text
batch_search 不是简单返回 JSON
它会先拿 result，再把每个 query 的文档结果格式化成字符串列表
```

---

## 22.4 第三步：_batch_search() 发 HTTP 请求

看：

- [`_batch_search()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:450)

```python
payload = {
    "queries": queries,
    "topk": self.config.topk,
    "return_scores": True
}

return requests.post(self.config.search_url, json=payload).json()
```

这里说明：

- `queries` 是一个字符串列表
- `topk` 来自训练配置
- `search_url` 也是从训练配置传进来的

如果当前查询只有一个，那么请求体大致是：

```json
{
  "queries": ["Mike Barnett CSKA Moscow general manager"],
  "topk": 3,
  "return_scores": true
}
```

返回值是一个 JSON，对应检索服务的：

- [`search_r1/search/retrieval_server.py`](/Users/icarus/Documents/Search-R1-main/search_r1/search/retrieval_server.py:358)

```python
return {"result": resp}
```

所以 `_batch_search()` 返回的最关键字段是：

```text
response_json["result"]
```

---

## 22.5 第四步：检索服务返回的 `result` 长什么样

`_batch_search()` 拿到的是整个 JSON，`batch_search()` 立即取：

```python
results = self._batch_search(queries)['result']
```

这个 `results` 可以理解成：

```text
[
  query1 的 topk 文档列表,
  query2 的 topk 文档列表,
  ...
]
```

如果只有一个 query，可能长这样：

```json
[
  [
    {
      "document": {
        "id": "123",
        "contents": "Mike Barnett\nMike Barnett is a sports agent..."
      },
      "score": 14.2
    },
    {
      "document": {
        "id": "456",
        "contents": "Sergei Fedorov\nSergei Fedorov later became..."
      },
      "score": 13.8
    }
  ]
]
```

接下来不会把这段 JSON 直接喂给模型，而是交给 `_passages2string()` 转成人能读的文本。

---

## 22.6 第五步：_passages2string() 先把文档转成纯文本

看：

- [`_passages2string()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:460)

```python
def _passages2string(self, retrieval_result):
    format_reference = ''
    for idx, doc_item in enumerate(retrieval_result):
        content = doc_item['document']['contents']
        title = content.split("\n")[0]
        text = "\n".join(content.split("\n")[1:])
        format_reference += f"Doc {idx+1}(Title: {title}) {text}\n"

    return format_reference
```

这里有三个关键点。

### 1. 它依赖的是 `document.contents`

不是 `title` 字段，不是 `text` 字段，而是：

```python
content = doc_item['document']['contents']
```

所以只要检索服务返回结构里缺少 `document.contents`，这里就会报错。

### 2. 它约定 `contents` 的第一行是标题

```python
title = content.split("\n")[0]
text = "\n".join(content.split("\n")[1:])
```

也就是说它假设 `contents` 长这样：

```text
Title
Passage text...
```

### 3. 它输出的是普通字符串

每篇文档会被变成：

```text
Doc 1(Title: Mike Barnett) Mike Barnett is a sports agent...
Doc 2(Title: Sergei Fedorov) Sergei Fedorov later became...
```

所以 `_passages2string()` 的作用就是：

```text
把检索服务返回的结构化文档列表
转成下一轮 prompt 可直接拼接的纯文本块
```

---

## 22.7 第六步：batch_search() 的最终返回值是什么

因为：

```python
return [self._passages2string(result) for result in results]
```

所以 `batch_search()` 返回的不是 JSON，而是：

```text
[
  "Doc 1(Title: ...)...\nDoc 2(Title: ...)...\n",
  "另一个 query 对应的文档字符串",
  ...
]
```

也就是说，到了 `execute_predictions()` 里，`search_results` 已经是一个字符串列表了。

这点要记清楚，因为后面拼 `<information>` 时直接用的是字符串，不再解析 JSON。

---

## 22.8 第七步：`<information>...</information>` 是在哪拼进去的

就在：

- [`execute_predictions()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:390)

```python
elif action == 'search':
    next_obs.append(f'\n\n<information>{search_results.pop(0).strip()}</information>\n\n')
    dones.append(0)
    valid_action.append(1)
    is_search.append(1)
```

这就是整个流程里最关键的一行之一。

它做了三件事：

1. 取出当前样本对应的检索结果字符串
2. 去掉首尾空白
3. 外面包一层 `<information>...</information>`

所以模型下一轮真正拿到的 observation 形如：

```text

<information>Doc 1(Title: Mike Barnett) Mike Barnett is a sports agent...
Doc 2(Title: Sergei Fedorov) Sergei Fedorov later became...</information>

```

也就是说：

```text
<information> 标签不是检索服务返回的
而是 generation.py 在 execute_predictions() 里拼进去的
```

这是很多人第一次看代码时容易混淆的点。

---

## 22.9 第八步：`next_obs` 这时还是字符串列表

在 `execute_predictions()` 结束时，返回的是：

```python
return next_obs, dones, valid_action, is_search
```

其中 `next_obs` 仍然是 Python 字符串列表，比如：

```python
[
  "\n\n<information>Doc 1 ...</information>\n\n",
  "",
  "\nMy previous action is invalid....\n"
]
```

注意：

- search 样本会拿到 `<information>...</information>`
- answer 样本会拿到空字符串
- 非法动作样本会拿到错误提示字符串

所以从环境交互视角看，`next_obs` 就是“系统对当前动作的反馈”。

---

## 22.10 第九步：_process_next_obs() 把 observation tokenize

回到主循环：

- [`run_llm_loop()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:264)

```python
next_obs_ids = self._process_next_obs(next_obs)
```

对应函数是：

- [`_process_next_obs()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:77)

```python
next_obs_ids = self.tokenizer(
    next_obs, 
    padding='longest',
    return_tensors='pt',
    add_special_tokens=False,
)['input_ids']
```

这一步做的事非常直接：

```text
把字符串形式的 observation
-> tokenize
-> pad 成一个 batch tensor
```

注意这里：

```python
add_special_tokens=False
```

说明 observation 在拼回上下文时不会额外自动加 BOS/EOS 一类特殊 token。

然后会做长度裁剪：

```python
if next_obs_ids.shape[1] > self.config.max_obs_length:
    next_obs_ids = next_obs_ids[:, :self.config.max_obs_length]
```

这表示：

```text
检索结果再长，也只保留前 max_obs_length 个 token
```

所以检索返回很多长文档时，真正进入下一轮上下文的可能只是前半部分。

---

## 22.11 第十步：_update_rolling_state() 把新 observation 拼回 input_ids

这是整个流程里最关键的状态更新函数：

- [`_update_rolling_state()`](/Users/icarus/Documents/Search-R1-main/search_r1/llm_agent/generation.py:93)

```python
def _update_rolling_state(self, rollings: DataProto, cur_responses: torch.Tensor, next_obs_ids: torch.Tensor) -> Dict:
```

核心拼接逻辑：

```python
new_input_ids = self.tensor_fn.concatenate_with_padding([
    rollings.batch['input_ids'],
    cur_responses,
    next_obs_ids
])
```

这句就是：

```text
旧 input_ids
+ 当前轮模型输出
+ 当前轮 observation
= 下一轮 input_ids
```

如果写成更直观的文本流程，就是：

```text
原 prompt
+ <search>...</search>
+ <information>Doc 1 ... Doc 2 ...</information>
= 下一轮上下文
```

然后它重新生成：

```python
new_attention_mask = self.tensor_fn.create_attention_mask(new_input_ids)
new_position_ids = self.tensor_fn.create_position_ids(new_attention_mask)
```

这说明下一轮不是简单拼字符串，而是重新构造了完整的模型输入三件套：

- `input_ids`
- `attention_mask`
- `position_ids`

---

## 22.12 第十一步：为什么还要裁剪到 `max_prompt_length`

在 `_update_rolling_state()` 里：

```python
effective_len = new_attention_mask.sum(dim=1).max()
max_len = min(self.config.max_prompt_length, effective_len)
```

然后：

```python
new_rollings = DataProto.from_dict({
    'input_ids': new_input_ids[:, -max_len:],
    'position_ids': new_position_ids[:, -max_len:],
    'attention_mask': new_attention_mask[:, -max_len:]
})
```

这里的含义是：

```text
随着多轮搜索进行，上下文会越来越长。
为了不超过模型允许的 prompt 长度，
系统只保留最后 max_len 个 token。
```

注意它取的是：

```python
[:, -max_len:]
```

也就是说保留的是**右侧最新的内容**，不是左侧最旧的内容。

这符合多轮 agent 的需求，因为最近一轮的 search 和 information 往往更重要。

---

## 22.13 第十二步：为什么这一步是项目最值得吃透的地方

因为这一步把三种系统拼起来了：

```text
1. LLM 文本生成
2. 外部工具调用
3. 多轮上下文管理
```

更具体地说：

- `batch_search()` 负责把内部动作变成外部服务调用
- `_passages2string()` 负责把结构化返回变成 LLM 可读文本
- `execute_predictions()` 负责包成 `<information>` observation
- `_process_next_obs()` 负责文本到 token 的转换
- `_update_rolling_state()` 负责把 observation 并回下一轮输入

如果你能讲清这五个函数的关系，你对 Search-R1 的核心 agent 机制就基本讲清了。

---

## 22.14 一个完整的小例子

假设当前 prompt 是：

```text
Question: Mike Barnett negotiated many contracts including which player that later became general manager of CSKA Moscow?
```

### 当前轮模型输出

```text
<search>Mike Barnett CSKA Moscow general manager</search>
```

### `execute_predictions()` 提取 query

```text
search_queries = ["Mike Barnett CSKA Moscow general manager"]
```

### `_batch_search()` 发请求

```json
{
  "queries": ["Mike Barnett CSKA Moscow general manager"],
  "topk": 3,
  "return_scores": true
}
```

### `_passages2string()` 格式化结果

```text
Doc 1(Title: Mike Barnett) Mike Barnett is a sports agent...
Doc 2(Title: Sergei Fedorov) Sergei Fedorov later became general manager of CSKA Moscow...
```

### `execute_predictions()` 包 observation

```text
<information>Doc 1(...) ... Doc 2(...) ...</information>
```

### `_process_next_obs()` tokenize

```text
字符串 observation -> next_obs_ids
```

### `_update_rolling_state()` 拼回上下文

```text
旧 prompt
+ <search>Mike Barnett CSKA Moscow general manager</search>
+ <information>Doc 1 ... Doc 2 ...</information>
= 下一轮 input_ids
```

然后模型下一轮就有条件直接输出：

```text
<answer>Sergei Fedorov</answer>
```

## 22.15 排查问题时先看什么

### 检索返回了，但模型下一轮像没看到

先看：

- `_process_next_obs()`
- `max_obs_length`
- `_update_rolling_state()`

重点检查 observation 是否被截断太狠。

### 检索服务返回 JSON 结构不对

先看：

- `_passages2string()`

重点检查：

```python
doc_item['document']['contents']
```

是否真的存在。

### `<information>` 没有出现在下一轮上下文里

先看：

- `execute_predictions()` 里是否走到了 `action == 'search'`
- `next_obs` 是否正确构造
- `_update_rolling_state()` 是否真的拼了 `next_obs_ids`

### 搜索结果过长，后文丢失

先看：

- `max_obs_length`
- `max_prompt_length`

因为这两处都会裁剪。

---

## 22.16 本章结论

这一步的核心不是“调了一次搜索”，而是：

**把结构化检索结果可靠地转成 LLM 下一轮可继续推理的上下文。**

可以压缩成一句话：

```text
Search-R1 先把检索结果从 JSON 转成 `Doc 1 / Doc 2` 文本，再包成 `<information>...</information>`，随后 tokenize 并和当前 response 一起拼回 `input_ids`，从而实现多轮 search-enhanced rollout。
```
